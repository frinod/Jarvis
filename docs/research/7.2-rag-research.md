## 1. Current Retrieval Flow Audit

The complete path from user input to LLM prompt in Phase 6:

```
ExecutionEngine._stage_memory()
  └── MemoryPipelineProvider.load(ctx)
        ├── ShortTermMemory.add(ctx.user_input)          ← records turn
        ├── ShortTermMemory.recent(n=10, session_id)     ← last N turns
        ├── EmbeddingService.top_k(query, all_ltm)       ← if LTM + embeddings
        └── ctx.memory_context = merged list             ← STM + LTM hits

ExecutionEngine._stage_respond()
  └── PipelineResponderAdapter.respond(ctx)
        └── SystemPromptBuilder.build(ctx)
              ├── [system]    template.render(agent_name, objective)
              ├── [user/asst] ctx.recent_history(6 turns)
              ├── [user]      "Relevant context:\n- [role] content\n..."  ← max 5 entries
              ├── [user]      "Reasoning so far:\nStep 0: ...\n..."       ← max 3 steps
              └── [user]      ctx.user_input
```

### Identified limitations

| # | Limitation | Impact |
|---|-----------|--------|
| L1 | Retrieval is a single-stage flat fetch — no re-ranking | Low-relevance entries pollute the prompt |
| L2 | `memory_context` is a flat list of `MemoryEntry` objects — no chunking | Long entries consume disproportionate context window |
| L3 | `SystemPromptBuilder` truncates to 5 entries with no relevance ordering | Most relevant entry may be entry #6 and silently dropped |
| L4 | No metadata filtering at retrieval time | Market data, news, and conversation turns compete equally |
| L5 | No semantic caching — identical queries re-retrieve and re-generate | Wasted LLM calls, latency, and cost |
| L6 | Perception data (market, news, sentiment) is not in the memory pipeline | `AnalystAgent` and `TraderAgent` cannot retrieve past market context |
| L7 | `SystemPromptBuilder` injects raw `MemoryEntry` text verbatim | No summarisation or compression before injection |
| L8 | No retrieval evaluation — no way to measure recall@k or MRR | Cannot know if retrieval is improving or degrading |

## 2. RAG Architecture Comparison

### 2.1 Naive RAG

**Pattern**: embed query → vector search → top-k → inject into prompt.

**Pros**: simple, well-understood, easy to implement.
**Cons**: single-stage, no re-ranking, no metadata filtering, precision degrades
at scale. This is essentially what Phase 6 does with `SimpleEmbeddingService`.

**Verdict**: already implemented (poorly). Not sufficient for Phase 7.

---

### 2.2 Hybrid RAG (BM25 + Dense Retrieval)

**Pattern**: run dense vector search AND sparse BM25 keyword search in parallel,
merge results with Reciprocal Rank Fusion (RRF) or weighted score.

**Research basis**: Karpukhin et al. (DPR, 2020), Ma et al. (SPLADE, 2022).
Hybrid consistently outperforms either alone on recall@10 by 5–15%.

**Fit for JARVIS**:
- Qdrant supports sparse vectors natively (v1.7+) — no second index needed.
- BM25 is critical for financial queries: exact ticker symbols (`RELIANCE`,
  `INFY`) are not semantically meaningful to dense models but are exact
  keyword matches.
- Python 3.7 compatible, offline, no extra services.

**Verdict**: **recommended for Phase 7**. Qdrant handles both in one query.

---

### 2.3 Graph RAG

**Pattern**: build a knowledge graph from documents; traverse graph edges
during retrieval to follow entity relationships.

**Research basis**: Edge et al. (Microsoft GraphRAG, 2024).

**Fit for JARVIS**:
- Requires a graph database (Neo4j, NetworkX) or graph construction pipeline.
- Significant build complexity: entity extraction, relation extraction, graph
  maintenance.
- High value for long-document corpora (research papers, annual reports).
- Low value for JARVIS Phase 7 which primarily retrieves short conversation
  turns and market snapshots.

**Verdict**: **defer to Phase 9+**. Revisit when JARVIS ingests long-form
research documents or builds a persistent knowledge base.

---

### 2.4 Agentic RAG

**Pattern**: an agent decides *whether* to retrieve, *what* to retrieve, and
*how many times* to retrieve (iterative retrieval). The agent can issue
multiple retrieval queries and synthesise results.

**Research basis**: Shinn et al. (Reflexion, 2023), Yao et al. (ReAct, 2022).

**Fit for JARVIS**:
- JARVIS already has `Brain` → `Coordinator` → `ExecutionEngine` — the
  agent loop is already present.
- Agentic RAG maps naturally onto the existing pipeline: the `PipelinePlanner`
  can decide retrieval strategy; the `PipelineToolRunner` can issue retrieval
  as a tool call.
- Iterative retrieval (retrieve → reason → retrieve again) fits the
  `MAX_REASONING_RETRIES` loop already in `ExecutionEngine._stage_reason()`.

**Verdict**: **partially adopt in Phase 7**. Wire retrieval as a tool so
agents can trigger targeted retrieval. Full iterative agentic RAG deferred
to Phase 8 (requires ReAct loop — see 7.3 Agent Research).

---

### 2.5 Hierarchical RAG

**Pattern**: two-stage retrieval — first retrieve document-level summaries,
then retrieve passage-level chunks from the selected documents.

**Research basis**: Raptor (Sarthi et al., 2024).

**Fit for JARVIS**:
- Valuable when the corpus contains long documents (>2000 tokens).
- Phase 7 corpus is primarily short entries (conversation turns, market
  snapshots, news headlines). Hierarchical retrieval adds overhead with
  minimal benefit at this scale.
- The `summarise_memory` template already exists in `TemplateRegistry` —
  the infrastructure for summarisation is present.

**Verdict**: **defer to Phase 8**. Adopt when JARVIS ingests long-form
documents (earnings reports, research notes).

---

### 2.6 Multi-Stage Retrieval (Retrieve → Re-rank → Filter)

**Pattern**: broad retrieval (top-20) → cross-encoder re-ranking → top-k
filtered result injected into prompt.

**Research basis**: Nogueira & Cho (2019), Pradeep et al. (2021).

**Fit for JARVIS**:
- Cross-encoder re-ranking requires a second model (~100 MB for
  `cross-encoder/ms-marco-MiniLM-L-6-v2`).
- Significant precision improvement over bi-encoder retrieval alone.
- Compatible with Python 3.7, offline, Windows.
- Fits cleanly into `MemoryPipelineProvider.load()` as a post-retrieval step.

**Verdict**: **adopt lightweight re-ranking in Phase 7** using a
`ReRanker` ABC with a `CrossEncoderReRanker` implementation. The ABC
allows a `NoOpReRanker` fallback when the model is not available.

## 3. Key RAG Design Decisions

### 3.1 Chunking Strategy

**Current**: entries stored whole. No chunking.

**Options**:
- Fixed-size (512 tokens, 64 overlap): simple, predictable.
- Sentence-boundary: preserves semantic units, variable size.
- Semantic chunking (embed + split on similarity drop): highest quality,
  requires embedding at ingest time.

**Recommendation**: sentence-boundary chunking for entries > 400 characters
at ingest time. Implemented in `QdrantLongTermMemory.store()` (Phase 7).
Semantic chunking deferred to Phase 8.

### 3.2 Metadata Filtering

**Current**: no filtering — all entry types compete equally.

**Recommendation**: tag every `MemoryEntry` with `entry_type` in metadata:
`"conversation"`, `"market_snapshot"`, `"news"`, `"analysis_result"`.

`MemoryPipelineProvider.load()` accepts an optional `entry_types` filter.
`AnalystAgent` requests `["market_snapshot", "analysis_result"]`.
`TraderAgent` requests `["market_snapshot", "news"]`.
Default (no filter): all types.

This requires no interface changes — `MemoryEntry.metadata` already exists.

### 3.3 Context Window Management

**Current**: `SystemPromptBuilder` injects up to 5 raw entries, truncated
by index (not by relevance or token count).

**Recommendation**:
- Inject entries in descending relevance score order (highest first).
- Add a `max_context_tokens` budget (default 800 tokens).
- Estimate token count as `len(content) // 4` (fast approximation).
- Stop injecting when budget is exhausted.
- This is a change to `BuilderConfig` and `SystemPromptBuilder._build_memory()`.

### 3.4 Re-ranking

**Recommendation**: `ReRanker` ABC with two implementations:
- `NoOpReRanker`: returns entries unchanged (default, zero overhead).
- `CrossEncoderReRanker`: uses `cross-encoder/ms-marco-MiniLM-L-6-v2`
  (~100 MB) to re-score top-20 candidates, returns top-5.

Injected into `MemoryPipelineProvider` as an optional collaborator.
Falls back to `NoOpReRanker` if model unavailable.

### 3.5 Semantic Caching

**Pattern**: before calling the LLM, check if a semantically similar query
was answered recently. If similarity > threshold, return cached response.

**Research basis**: GPTCache (Bang et al., 2023).

**Fit for JARVIS**:
- High value for repeated market queries (`"What is RELIANCE doing?"` asked
  multiple times per session).
- Cache key = embedding of `ctx.active_goal`, similarity threshold = 0.92.
- Cache store = in-memory dict with TTL (5 minutes for market data,
  30 minutes for general queries).
- Implemented as a `SemanticCache` class injected into `LLMGateway` or
  `PipelineResponderAdapter`.

**Verdict**: **adopt in Phase 7**. Significant latency and cost reduction
for the Angel One trading workflow.

### 3.6 Retrieval Evaluation Metrics

To know if RAG is improving, measure:

| Metric | What it measures | How to compute |
|--------|-----------------|----------------|
| Recall@k | Are relevant entries in top-k? | Requires labelled test set |
| MRR | Mean Reciprocal Rank of first relevant result | Requires labelled test set |
| Context precision | Fraction of retrieved entries that are relevant | LLM-as-judge or manual |
| Faithfulness | Does response match retrieved context? | LLM-as-judge |

**Phase 7 scope**: implement `RetrievalEvaluator` with a small labelled
test set (20–30 query/relevant-entry pairs). Run as part of the test suite.
Full RAGAS-style evaluation deferred to Phase 8.

## 4. Integration Map

How RAG connects to existing JARVIS components:

```
Brain.process()
  └── ExecutionEngine.run()
        ├── _stage_plan()      ← PipelinePlanner sets ctx.intent_type
        │                         → determines retrieval filter (entry_types)
        │
        ├── _stage_memory()    ← MemoryPipelineProvider.load(ctx)
        │     ├── STM.recent()                    ← conversation turns
        │     ├── QdrantLTM.search(hybrid)        ← dense + sparse (Phase 7)
        │     ├── ReRanker.rerank(query, hits)    ← cross-encoder (Phase 7)
        │     └── ctx.memory_context = top-k      ← relevance-ordered
        │
        ├── _stage_tools()     ← ToolRunner can call RetrievalTool
        │                         (agentic RAG: agent-triggered retrieval)
        │
        ├── _stage_reason()    ← ChainOfThought reads ctx.memory_context
        │                         (memory boost already wired)
        │
        └── _stage_respond()   ← SystemPromptBuilder.build(ctx)
              └── injects ctx.memory_context (relevance-ordered, token-budgeted)
```

**Market Intelligence integration**:
- `MarketPerception.fetch()` results stored as `MemoryEntry` with
  `entry_type="market_snapshot"` at the end of each request.
- `NewsPerception.fetch()` results stored as `entry_type="news"`.
- `AnalystAgent` and `TraderAgent` retrieve these via metadata filter.

## 5. Phase 7 vs Phase 8 Scope

### Phase 7 (implement)

| Item | Complexity | Value |
|------|-----------|-------|
| Hybrid RAG (Qdrant sparse + dense) | Medium | High |
| Metadata filtering by `entry_type` | Low | High |
| Relevance-ordered context injection | Low | High |
| Token-budget context window management | Low | Medium |
| `ReRanker` ABC + `CrossEncoderReRanker` | Medium | High |
| `SemanticCache` in `LLMGateway` | Medium | High |
| Perception data → LTM pipeline | Low | High |
| `RetrievalEvaluator` (small test set) | Low | Medium |

### Phase 8 (defer)

| Item | Reason for deferral |
|------|-------------------|
| Full iterative agentic RAG (ReAct loop) | Requires Phase 7 agent framework first |
| Graph RAG | Requires knowledge graph infrastructure |
| Hierarchical RAG | Requires long-document corpus not yet present |
| Semantic chunking at ingest | Adds embedding cost at write time |
| Full RAGAS evaluation suite | Requires labelled dataset at scale |

## 7. Risks

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| `cross-encoder` model ~100 MB download | Medium | `NoOpReRanker` fallback; download on demand |
| Qdrant sparse vector API instability | Low | Pin `qdrant-client==1.7.x`; integration test |
| Semantic cache false positives (threshold too low) | Medium | Default threshold 0.92; configurable; unit tested |
| Token budget estimation inaccurate | Low | `len // 4` is conservative; real tokeniser in Phase 8 |

---

## 8. Decision

**Adopt**: Hybrid RAG (Qdrant sparse+dense), metadata filtering, re-ranking
(`ReRanker` ABC), semantic caching, token-budgeted context injection,
perception-to-LTM pipeline.

**Reject for Phase 7**: Graph RAG, Hierarchical RAG, full iterative agentic RAG.

See `docs/adr/ADR-003-rag.md` for the formal decision record.
