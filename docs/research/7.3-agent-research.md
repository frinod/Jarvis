### Known limitations

1. **All agents are stubs** — `execute()` returns hardcoded strings. No real
   reasoning, no LLM calls, no tool use inside agents.
2. **`CapabilityMatchPolicy` scores near-zero** — `intent_type` and
   `required_capabilities` are not populated in `Goal.metadata` from the
   current orchestrator path (confirmed in pre-Phase 7 audit).
3. **`capabilities` is a mutable class variable** on `BaseAgent` — shared
   across all instances of the same class (known bug).
4. **No agent-level tool use** — agents cannot call `AIToolRegistry` from
   within `execute()`. Tools are only reachable via `PipelineToolRunner`.
5. **No agent-level memory access** — agents cannot query `LongTermMemory`
   directly. Memory is loaded once at pipeline start.
6. **`WorkflowEngine` is sequential only** — `depends_on` is modelled but
   `asyncio.gather()` is not wired. Parallel execution is Phase 7 target.
7. **`AgentMetrics` collected but unused** — `success_rate` and
   `avg_latency_ms` are not fed back into `CapabilityMatchPolicy`.
8. **No agent communication** — agents cannot pass results to each other
   within a workflow. Each node is independent.

## 2. Research Findings

### 2.1 ReAct (Reason + Act)

**Pattern** (Yao et al., 2022): interleave reasoning steps (Thought) with
action steps (Act: tool call) and observation steps (Observe: tool result).
Loop until goal is achieved or max steps reached.

```
Thought: I need the current price of RELIANCE.
Act: call market_data_tool(symbol="RELIANCE")
Observe: {"price": 2847.50, "change": +1.2%}
Thought: Price is up 1.2%. RSI from memory is 68. Approaching overbought.
Act: call memory_search(query="RELIANCE RSI history")
Observe: [entry: "RSI was 72 last week, pulled back"]
Thought: Pattern suggests short-term resistance. Signal: HOLD.
Final Answer: HOLD — approaching overbought territory.
```

**Fit for JARVIS**:
- Maps directly onto `BaseAgent.execute()` → tool calls → `verify()` loop.
- `AIToolRegistry` already provides the tool execution layer with timeout
  and error isolation.
- `ExecutionEngine._stage_reason()` already has a retry loop
  (`MAX_REASONING_RETRIES=2`) — this becomes the ReAct loop.
- The LLM generates Thought steps; `AIToolRegistry.call()` executes Act steps.

**Verdict**: **adopt ReAct as the Phase 7 agent execution model** for
`TraderAgent` and `AnalystAgent`. Implement as `ReactExecutor` injected
into agent `execute()`.

### 2.2 Tool-Calling Agents vs Function-Calling APIs

Modern LLMs (GPT-4, Gemini 1.5, Groq/Llama-3) support native function
calling: the model returns a structured JSON tool call instead of text.

**Fit for JARVIS**:
- `GeminiProvider` and `OpenAICompatibleProvider` both support function
  calling via their APIs.
- `AIToolRegistry` already has the tool schema — needs a `to_schema()` method
  to emit OpenAI-compatible function definitions.
- Native function calling is more reliable than parsing tool calls from
  free-form LLM text.

**Verdict**: **adopt native function calling in Phase 7** for providers that
support it. `AIToolRegistry.to_schema()` emits the tool definitions.
`LLMGateway` passes them in the request. Fallback: text-based tool parsing
for providers that don't support it (Ollama).

### 2.3 Multi-Agent Coordination

**Pattern**: multiple specialised agents collaborate on a single goal.
Agent A produces output that Agent B consumes.

**Current state**: `WorkflowEngine` nodes are independent — no result passing.
`BrainCapabilities.supports_multi_agent = False`.

**Options**:
- **Sequential handoff**: Agent A result stored in `ExecutionContext.metadata`,
  Agent B reads it. Simple, no new infrastructure.
- **Shared blackboard**: agents write to a shared `WorkflowContext` dict.
  More flexible, slightly more complex.
- **Message passing**: agents send typed messages to each other via an
  internal bus. Most flexible, most complex.

**Fit for JARVIS Phase 7**:
- Sequential handoff via `ExecutionContext.metadata` is sufficient for the
  current workflow patterns (Researcher → Analyst → Trader).
- No new infrastructure needed — `WorkflowNode.result` already exists.
- Full message-passing deferred to Phase 8.

**Verdict**: **adopt sequential handoff in Phase 7**. Wire
`WorkflowEngine._run_node()` to pass `node.result` into the next node's
`ExecutionContext.metadata`.

### 2.4 Parallel Agent Execution

`WorkflowEngine` already models `depends_on` per node. The sequential loop
is the only thing preventing parallel execution.

**Phase 7 change**: replace the sequential `for node in workflow.nodes` loop
with a topological sort + `asyncio.gather()` over nodes whose dependencies
are satisfied. No data model changes required (confirmed in workflow.py
docstring: "Phase 7 parallel execution: replace the sequential loop with
asyncio.gather()").

**Verdict**: **implement parallel execution in Phase 7**. Estimated ~40 lines
of change to `WorkflowEngine.run()`.

### 2.5 Agent Capability Scoring Fix

`CapabilityMatchPolicy` scores near-zero because `Goal.metadata` does not
contain `intent_type` or `required_capabilities` when called from the
current orchestrator path.

**Fix**: `PipelinePlannerAdapter.plan()` already sets `ctx.intent_type`.
Wire this into `Goal.metadata` before `Coordinator.select()` is called.
Specifically: in `Brain.process()`, after `ExecutionEngine` runs the plan
stage, copy `ctx.intent_type` into `goal.metadata["intent_type"]`.

This is a 2-line fix in `brain.py` — no interface changes.

**Verdict**: **fix in Phase 7** as part of agent framework work.

### 2.6 AgentMetrics → SelectionPolicy Feedback

`AgentMetrics` tracks `success_rate`, `avg_latency_ms`, `avg_confidence`
but `CapabilityMatchPolicy` ignores them.

**Phase 7**: add a `metrics_weight` to `SelectionWeights` (default 0.0 to
preserve current behaviour). When `AgentMetrics.requests >= 10`, incorporate
`success_rate` into the score. This enables data-driven agent selection
without breaking existing tests.

**Verdict**: **implement in Phase 7** with `metrics_weight=0.0` default
(backward compatible).

### 2.7 DSPy (Declarative Self-improving Python)

**Pattern** (Khattab et al., 2023): define agent behaviour as a declarative
program; DSPy optimises prompts automatically using a small labelled dataset.

**Fit for JARVIS**:
- Requires a labelled dataset of (input, expected_output) pairs.
- Adds a new dependency (`dspy-ai`).
- High value for optimising `TraderAgent` signal generation prompts.
- Python 3.7 compatible.

**Verdict**: **defer to Phase 8**. Requires labelled trading outcome data
that does not yet exist. Revisit after Phase 7 agents are producing real
outputs.

### 2.8 MCP (Model Context Protocol)

**Pattern** (Anthropic, 2024): standardised protocol for LLMs to call
external tools and data sources via a JSON-RPC-like interface.

**Fit for JARVIS**:
- `AIToolRegistry` already implements the same concept internally.
- MCP would allow JARVIS tools to be exposed to external MCP-compatible
  clients (Claude Desktop, etc.).
- Adds a new dependency and server infrastructure.

**Verdict**: **defer to Phase 9**. JARVIS tools are internal; no external
MCP clients are in scope for Phase 7.

## 3. Recommended Architecture for Phase 7

```
Brain.process()
  └── Coordinator.select(goal)          ← fixed: intent_type in goal.metadata
        └── AgentRegistry.available()   ← health + metrics-weighted scoring
              └── CapabilityMatchPolicy ← intent + capability + priority + metrics

WorkflowEngine.run(workflow)
  └── topological_sort(nodes)           ← Phase 7: parallel execution
        └── asyncio.gather(ready_nodes)
              └── ExecutionEngine.run() ← per node
                    └── ReactExecutor   ← Thought → Act → Observe loop
                          └── AIToolRegistry.call()  ← native function calling
```

### What does NOT change

- `BaseAgent` ABC — no changes.
- `AIToolRegistry` interface — `to_schema()` is additive.
- `WorkflowNode` data model — no changes.
- `AgentRegistry` — no changes.
- All 1517 existing tests — no modifications needed.

## 4. Phase 7 vs Phase 8 Scope

### Phase 7
- ReAct executor for `TraderAgent` and `AnalystAgent`
- Native function calling via `AIToolRegistry.to_schema()`
- Parallel workflow execution via `asyncio.gather()`
- Sequential result handoff between workflow nodes
- `CapabilityMatchPolicy` intent fix (2 lines)
- `AgentMetrics` feedback into scoring (metrics_weight=0.0 default)

### Phase 8+
- DSPy prompt optimisation
- MCP protocol exposure
- Full message-passing multi-agent communication
- Agent self-modification / meta-learning

## 5. Risks

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| ReAct loop exceeds `MAX_REASONING_RETRIES` | Medium | Cap at 3 iterations; return best partial result |
| Parallel workflow introduces race conditions on `ExecutionContext` | Low | Each node gets its own `ExecutionContext` instance |
| Native function calling not supported by Ollama | Known | Text-based fallback parser in `ReactExecutor` |
| `asyncio.gather()` masks individual node errors | Low | Wrap each gather task in try/except; propagate to `NodeRecord` |
