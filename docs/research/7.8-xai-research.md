## 1. Current Implementation Audit

### What exists (Phase 6)

| Component | Explanation capability |
|-----------|----------------------|
| `ExecutionTrace` | Per-stage timing, tools used, skills used, retry count |
| `WorkflowTrace` | Per-node timing, status, agent assignment |
| `DecisionRecord` | Goal ID, decision type, source, rationale, outcome |
| `ReflectionResult` | Critique string, action items, confidence delta |
| `AgentResult.explanation` | Free-text explanation from agent |
| `VerificationResult.critique` | Reasoning quality critique |
| `SelectionResult` | Full agent scoring rationale |
| `ThoughtStep` | Content + confidence per reasoning step |
| `TradeSignal.rationale` | "High confidence (82%) supports a buy signal." |
| `ConfidenceScorer.ScoredResult.reasoning` | "Aggregated from: prediction=0.78, ta=0.65 → 73%" |

### Key observation

JARVIS already has extensive explanation infrastructure. The data is
collected at every stage. The gap is that this data is:
1. Not surfaced to the user in a structured, readable format.
2. Not included in the LLM response prompt.
3. Not accessible via any API endpoint beyond `/api/ai/runtime/status`.

**Phase 7 XAI task**: surface the existing explanation data, not build
new explanation infrastructure.

## 2. Research Findings

### 2.1 XAI for LLM-Based Systems

For LLM-based systems, XAI has two distinct layers:

**Layer 1 — Process transparency**: explain *how* the system arrived at
its answer (which tools were called, which memories were retrieved, what
the reasoning chain was). JARVIS already collects all of this.

**Layer 2 — Model interpretability**: explain *why* the LLM produced a
specific token sequence. This requires attention visualisation or probing
classifiers — not applicable to black-box API providers.

**Phase 7 scope**: Layer 1 only. Layer 2 is not feasible with API-based
LLMs and is deferred indefinitely.

### 2.2 XAI for XGBoost Predictions

XGBoost supports SHAP (SHapley Additive exPlanations) values natively via
`xgboost.get_booster().predict(pred_contribs=True)`.

SHAP values answer: "Which features contributed most to this prediction?"

**Example output**:
```
RELIANCE prediction: UP (confidence 78%)
Top contributing features:
  RSI=68.2        → +0.12 (approaching overbought, momentum positive)
  MACD=+0.45      → +0.09 (bullish crossover)
  Volume ratio=1.8x → +0.07 (above-average volume confirms move)
  EMA9 > EMA21    → +0.05 (short-term trend positive)
  BB position=0.72 → -0.03 (near upper band, some resistance)
```

**Fit for JARVIS**:
- `xgboost` already installed (models exist).
- SHAP computation adds ~5–20 ms per prediction.
- Python 3.7 compatible.
- Output maps directly to `TradeSignal.rationale` — replaces the current
  generic "High confidence (78%) supports a buy signal."

**Verdict**: **implement SHAP-based rationale in Phase 7** for
`XGBoostForecastingEngine`. The rationale string is stored in
`PredictionResult.metadata["shap_explanation"]` and surfaced in
`TradeSignal.rationale`.

### 2.3 Confidence Decomposition

`ConfidenceScorer.ScoredResult` already contains `components` dict:
`{"prediction": 0.78, "ta_signal": 0.65, "sentiment": 0.42}`.

**Phase 7**: surface this decomposition in the agent response. Instead of:
> "Signal: BUY (confidence 73%)"

Produce:
> "Signal: BUY (confidence 73%) — Model: 78%, TA: 65%, Sentiment: 42%"

This is a formatting change in `TraderAgent.execute()`, not new infrastructure.

### 2.4 Decision Trace API

`Brain._decision_history` and `ExecutionTrace` contain the full audit trail
for every request. Currently only accessible via `Brain.decisions_for_goal()`.

**Phase 7**: add `GET /api/ai/decision-trace/{request_id}` endpoint that
returns the `ExecutionTrace` + `DecisionRecord` list for a given request.

This enables the frontend to show a "Why did JARVIS say this?" panel.

**Verdict**: **implement decision trace endpoint in Phase 7**.

### 2.5 Counterfactual Explanations

**Pattern**: "What would have changed the prediction?" e.g., "If RSI were
below 60 instead of 68, the signal would be HOLD instead of BUY."

**Fit for JARVIS**:
- Requires perturbing feature values and re-running inference.
- Adds significant complexity.
- High user value for trading decisions.

**Verdict**: **defer to Phase 8**. Implement after SHAP is working and
user feedback confirms demand.

### 2.6 Natural Language Explanations

The LLM can be prompted to explain the reasoning in natural language:
"Given these SHAP values and TA signals, explain this trade recommendation
in 2–3 sentences for a retail investor."

**Fit for JARVIS**:
- One additional LLM call per trade signal.
- High user value — replaces technical jargon with plain English.
- The `explain()` method on `BaseAgent` is already in the contract.

**Verdict**: **implement NL explanation in Phase 7** for `TraderAgent`.
Wire `BaseAgent.explain()` to produce an LLM-generated explanation using
the SHAP values and confidence decomposition as input.

## 3. Recommended Architecture for Phase 7

```
TraderAgent.execute(ctx)
  └── XGBoostForecastingEngine.predict(features)
        └── model.predict_proba(features)
        └── model.get_booster().predict(pred_contribs=True)  ← SHAP
        └── PredictionResult(
              direction=UP,
              confidence=0.78,
              metadata={"shap_explanation": "RSI=68 (+0.12), MACD=+0.45 (+0.09)..."}
            )
  └── ConfidenceScorer.score() → ScoredResult(components={...})
  └── TradeSignal(
        direction=BUY,
        confidence=0.73,
        rationale="BUY (73%) — Model:78% TA:65% Sentiment:42% | " +
                  shap_explanation
      )

TraderAgent.explain(result)
  └── LLMGateway.complete(
        "Explain this trade signal in plain English: " + rationale
      )
  └── return NL explanation

GET /api/ai/decision-trace/{request_id}
  └── Brain.decisions_for_goal(goal_id)
  └── ExecutionTrace from result
  └── return structured JSON
```

### What does NOT change

- `BaseAgent.explain()` contract — no changes (implementations change).
- `PredictionResult` data model — `metadata` field already exists.
- `TradeSignal` data model — `rationale` field already exists.
- All existing tests — no modifications needed.

## 4. Phase 7 vs Phase 8 Scope

### Phase 7
- SHAP-based feature importance in `TradeSignal.rationale`
- Confidence decomposition in agent responses
- NL explanation via `BaseAgent.explain()` + LLM
- Decision trace API endpoint

### Phase 8+
- Counterfactual explanations ("what would change this signal?")
- Attention visualisation (local models only)
- Explanation quality evaluation (user feedback loop)
- XAI dashboard in frontend HUD

---

## 5. Risks

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| SHAP computation adds 5–20 ms per prediction | Low | Acceptable; cache SHAP values with feature vector cache |
| NL explanation LLM call adds latency | Medium | Make optional; configurable via `BuilderConfig.include_explanation` |
| SHAP values confuse non-technical users | Medium | NL explanation layer translates to plain English |
